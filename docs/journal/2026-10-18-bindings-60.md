# 2026-10-18: Binding ergonomics: defaults, objects, counters, anchors, Pydantic

This entry covers issue #39: the conveniences the essays sketch for
application code. It records what landed and the decisions behind it. The
rules for defaults and environments are in
[SEMANTICS.md §3.1–3.2](../SEMANTICS.md#31-defaults).

Labels: **[Fact]**, **[Measured]**, **[Interpretation]**, **[Proposal]**, **[Decision]**.

---

## What landed

**[Fact]** Five pieces:

- **Defaults:** `Param(..., default=...)`, and the same keyword on the kind
  helpers.
  - `required_params()` lists the parameters without one.
  - `PathExpr.defaults` lists the rest.
- **Bindings from objects:** every method that takes a mapping of bindings
  also takes an object, and `wend.bindings(obj)` shows what it binds.
- **Counters:** `wend.counter("chunk", width=3, of_total=True, suffix=".parquet")`
  is `chunk_{idx:03d}-of-{total:03d}.parquet`.
- **Anchors:** `wend.anchors` declares `HOME`, `CWD` and `XDG.*` as parameters.
  `anchors.bindings()` reads their values from the environment.
- **Pydantic:** `wend.pydantic.PathOf(expr)` validates a path field against
  a layout. wend's conditions validate as Pydantic metadata:
  `Annotated[Path, File, Exists]`. Both sit behind the new `pydantic` extra.

The essays' examples, as they now read:

| essay | wend |
|---|---|
| Part 1, `PathVar` | `CONFIG = ROOT / "config.yaml"`; `CONFIG.resolve(settings)` with `settings` a dataclass or model |
| Part 1, anchors | `fragment.under(XDG.CACHE_HOME / "myapp")`, rendered with `anchors.bindings()` |
| Part 3, sized counter | `root / "chunks" / counter("chunk", width=3, of_total=True, suffix=".parquet")` |
| Part 3, unsized counter | `root / "logs" / counter("log", width=5, suffix=".parquet")` |

`examples/bindings_and_anchors.py` runs all four, plus a Pydantic model.

## Decisions

### Defaults

**[Decision]** A default stands in for an absent binding *when a path is
rendered*, and nowhere else. That covers every route that renders:
- `render` and `resolve`;
- compiled renderers;
- `Under` bases;
- a lens's target;
- `resolve_frame`, for a parameter with no column.

The rule is one sentence in §3.1. Rendering with `env` is rendering with
`env⁺`, the environment extended by the defaults of the names it leaves
unbound. Every §6 obligation therefore carries over unchanged, and the
reference evaluator needed a single helper, `_value`, used in its three
lookups.

**[Decision]** `bind` does not apply defaults. `bind` is partial evaluation:
it fixes what it is given and leaves the rest symbolic. Applying defaults
there would make `e.bind(root=...)` silently fix every defaulted parameter.
Later bindings could then no longer override a default, and `bind` followed
by `render` would differ from `render`. `e.bind(e.defaults)` applies them
explicitly when that is wanted.

**[Decision]** Matching does not use defaults, and a default never makes a
part of a path optional. The issue asked whether a default is recovered or
verified. It is neither:
- every part of the path is read, defaulted or not;
- the value the path holds is returned, even when it differs from the default;
- verification renders with that complete binding, so no default enters it.

An optional part is a different construct. It is `Alt("", x)` in a union
(§11), and its readings are explicit. Making defaults imply optionality would
give `{x}` two readings of a path wherever `x` has a default, and §7 refuses
to choose between readings.

**[Decision]** `glob` does not fix an unbound defaulted parameter to its
default either: it discovers its values, as for any free parameter. An
unbound head is still an error. Its message now says that defaults are not
applied, and that `e.bind(e.defaults)` applies them.

**[Decision]** A default is part of the declaration. Two declarations that
differ only in their defaults conflict under the existing
`ParamConflictError` rule.

Defaults compare by type and `repr` as well as by value:
- `1`, `True` and `1.0` compare equal but render as `1`, `True` and `1.0`;
- the same holds for `0.0` and `-0.0`, and for `Decimal("1.0")` and `Decimal("1.00")`.

Value equality alone would break the template cache, which keys on equal
parameters. With the dataclass's equality patched back in,
`T(t"x{Param('n', default=True)}")` built after `T(t"x{Param('n', default=1)}")`
reuses the first parameter and renders `x1`. A test covers the case.

`Param` now writes `__eq__` and `__hash__` instead of taking the dataclass's.
`__eq__` checks identity first. That makes the common case in `_join`'s
table merge, a parameter compared with itself, cheaper than before.

**[Decision]** A default is validated at declaration as far as the
declaration alone decides:
- `type` and `choices`;
- hashability, because declarations are hashed with the expressions that use them;
- for an explicit kind, the kind's rule (`seg_value`, `splice_value`, `head_value`).

An `AUTO` parameter's kind depends on its position, so its default only has
to be usable somewhere: a path, or a value a segment can format. Wherever the
parameter is used, its default is checked again like any binding. An `AUTO`
default of `"/srv"` is valid at the head and invalid below it. The contract
generator includes such a parameter (`DROOT`), so the reference evaluator
checks both outcomes.

**[Decision]** The compiled fast path reads a defaulted parameter as
`env[name] if name in env else _default(p, env)`. A mapping keyed by `Param`
binds the parameter under its declaration, not its name, and the fast path
would miss that binding and use the default. `_default` therefore bails to
the interpreter when any key is a `Param`. It scans the keys only when a
default is needed. Expressions without defaults generate the same code as
before.

### Bindings from objects

**[Decision]** Objects are accepted directly, wherever a mapping is: `render`,
`resolve`, `bind`, `glob`, `check`, compiled renderers, unions, lenses and
steps. `wend.bindings(obj)` is the documented conversion, and shows what an
object binds. Both routes share one function, so they cannot disagree.

The `Mapping` path costs one `type(m) is not dict` test before
`isinstance(m, Mapping)`. Objects reach the compiled fast path through its
fallback: the generated function fails on an object, and the fallback
converts it and calls the fast function again.

**[Decision]** An object binds its *declared fields*, not arbitrary
attributes:
- a dataclass's `fields()`;
- attrs's `__attrs_attrs__`;
- Pydantic's `__pydantic_fields__`, plus extra fields;
- a named tuple's `_fields`;
- otherwise `vars(obj)`.

Looking attributes up by parameter name was the alternative. It needs no
field discovery, but it binds methods and properties. A parameter named
`count` would bind a named tuple's `count` method. A parameter named `copy`
or `schema` would bind a Pydantic model's method.

**[Fact]** The first version included Pydantic computed fields. Part 1's
`PathVar` example, written as a model whose computed field returns
`CONFIG.resolve(self)`, then recursed: reading the model's bindings
evaluated the computed field itself. Computed fields are now excluded, like
properties, and the example is a test.

**[Decision]** `None` in a field is a value, not an absent binding. §3 already
formats `None` as `"None"` at a segment position, and a declared `type=`
rejects it. Treating `None` as absent only for objects would give one
environment two meanings depending on how it was passed. §3.2 says so.

**[Decision]** Things that are not bindings are rejected with a `TypeError`
that names the problem:
- a `str`, `bytes` or path-like, which is usually a path passed where its
  name was meant;
- a class, which needs an instance;
- an object without fields or `__dict__`.

Before this change, any falsy value was silently treated as no bindings.

### Counters

**[Decision]** `counter` is one function, not a family of types. `of_total`
selects the sized form, `width` the padding, and `idx`/`total` the
parameters, as names or as `Param`s. A `Param` passed in keeps its default.
Every number is an integer field with a `d` spec, followed by a literal that
does not start with a digit. Counters therefore match on the fast path (§8),
and a test checks this.

### Anchors

**[Decision]** Anchors live in their own module, `wend.anchors`. Each is an
`Absolute` parameter named after its environment variable:
`{XDG_CACHE_HOME}`, `{HOME}`, `{CWD}`. Expressions built on them stay pure,
symbolic and matchable. Nothing reads the environment until
`anchors.bindings()` is called, and a test binds them like any parameter.

The alternatives were:
- **Defaults read at import:** frozen at import time, and impure.
- **Functions returning concrete expressions:** they read the environment at
  construction and lose the late binding Part 1 asks for.

**[Decision]** The XDG anchors follow the XDG Base Directory specification
on every POSIX platform, macOS included:
- the variable is used when it is set to an absolute path;
- an unset, empty or relative variable falls back to the default below `HOME`.

`~/Library/...` conventions are a different concept, which platformdirs
covers. A user who wants them binds the anchor to platformdirs' value.

`HOME` comes from `$HOME`, falling back to the password database. `CWD` is
`os.getcwd()`. It is omitted when the working directory no longer exists, so
only expressions that use it fail.

### Pydantic

**[Decision]** `PathOf(expr)` takes two kinds of input:
- **A path** must have exactly one reading. No reading and several readings
  are validation errors with distinct types (`wend_no_match`,
  `wend_ambiguous`).
- **Bindings** (a mapping, or an object such as another model) are rendered
  through `expr` when the model is validated. This is the `ImportString`
  analogy from Part 1.

Either way, `expr`'s preconditions (`requires`) are then checked. The
field's annotation picks the value: `Path` (or any `PurePath` class), `str`,
or `wend.Match`, which carries the bindings. In JSON every form serialises
to the path string, and the JSON schema records the pattern as
`x-wend-pattern`.

**[Decision]** A declaration that cannot work, such as a pattern with a
deferred head that `match` cannot invert, raises `NotInvertibleError` as it
is. Pydantic passes non-`ValueError` exceptions through, so the error reports
the schema, not the data.

**[Decision]** Conditions carry Pydantic's `__get_pydantic_core_schema__`
hook. The hook imports `wend.pydantic` only when Pydantic calls it, so the
core module has no Pydantic dependency. This makes the conditions journal's
observation real: `Annotated[Path, File, Exists]` is Pydantic's `FilePath`.

An `Under` whose base has parameters has no bindings to render the base with
in a bare annotation. It is refused when the model class is built, with a
pointer to `PathOf(expr.requires(Under(...)))`.

**[Fact]** Pydantic 2.14.1 and attrs 26.1.0 are in the test dependency group
and resolve for both 3.14 and 3.15: pydantic-core 2.50.1 ships `cp315`
wheels. `tests/pydantic_test.py` skips when Pydantic is absent.

## Tests and measurements

**[Fact]** The reference evaluator applies defaults through `_value`. The
contract generator adds seven defaulted parameters:
- operands of every kind, including the `AUTO` default that is valid only at
  the head;
- an integer field;
- a nested spec parameter;
- a free string field.

Environments leave each defaulted name unbound at random. Three properties
are new:
- rendering with defaults equals rendering with them bound explicitly. This is
  checked for the interpreter, the compiled renderer, and the compiled
  renderer given `Param` keys;
- `bind` leaves exactly the omitted defaulted parameters free, with their
  declarations;
- every reading of a rendering binds every parameter, and renders back.

**[Measured]** Stress runs at 5,000 examples each passed:
- the three new properties;
- `test_contract`;
- `test_compiled_obeys_the_contract_too`.

In the contract generator's own mix, about 10% of examples apply a default.
A second run built terms mostly from defaulted parameters, with every
defaulted name unbound, and passed 5,000 examples:

| outcome | cases |
|---|---:|
| reference renders, using defaults | 1,402 |
| reference renders, no default left after folding | 1,280 |
| reference rejects a binding, using defaults | 487 |
| reference rejects a binding, no default left | 183 |
| operation error | 394 |
| did not build | 1,254 |

Of these, 1,863 renderings also had their readings checked.

**[Interpretation]** The compiled renderer generates identical code on both
branches for an expression without defaults. Its rows differ by about 1–2%,
which is the noise floor. Every row without a parameter declaration in its
loop is within that floor.

Declaring a `Param` costs about 0.13 µs more (+7%). That is the frozen
dataclass's extra field and the check for a default. "Construct + render
nested SubPath" declares a `SubPath` inside its loop, which accounts for its
difference. The same case with the parameter declared once is level.

**[Measured]** What the new features cost when they are used. Minimum of
15 × 20,000 calls on this branch, shard expression:

| case | ns |
|---|---:|
| render, all bound, no default declared | 7,299 |
| render, all bound, `total` declares a default | 7,418 |
| render, `total`'s default applied | 7,657 |
| compiled, all bound, no default declared | 1,792 |
| compiled, all bound, `total` declares a default | 1,827 |
| compiled, `total`'s default applied | 2,129 |
| render from a dataclass | 9,047 |
| compiled from a dataclass | 3,649 |

The first version of object bindings measured 10,981 interpreted and 5,529
compiled. It detected the object's kind and listed its fields on every call.
A per-class plan, cached like the literal and template caches, brought them
to the numbers above.

The compiled route still pays for one failed attempt at the fast path: an
object is not subscriptable. Converting objects before the attempt would
cost every mapping a type test. The mapping path stays as it was.

## Open threads

**[Proposal]** Scaffolding (§12) creates an entry with unbound parameters once
per combination of their declared `choices`, and skips a parameter without
choices. A parameter with a default but no choices could be scaffolded at its
default. I left it out: §12 would change, and nothing in #39 asks for it.

**[Proposal]** Environment-style mappings (`os.environ`) are mappings and are
accepted already. A prefix-stripping view (`MYAPP_ROOT` binds `root`) is the
pydantic-settings convention. It is small, but it adds API surface no example
needs yet.

**[Interpretation]** `PathOf` has no access to sibling fields, so it renders
bindings given in the field's own input. Rendering from the model's other
fields is the computed-field pattern (`CONFIG.resolve(self)`), which objects
as bindings make a one-liner. Pydantic's `ValidationInfo.data` could make
the field-level route work too. That would bind a field to the order of the
fields declared before it, so I left it out.
