# 2026-10-18: Conditions, and what can be checked when

This entry covers issue #27: paths that carry *necessity and possibility*, from
[Future Paths part 1](https://cog.spin.systems/future-paths-types). It records:
- what landed;
- the decisions behind it;
- the measurements;
- the design note the issue asked for, on what a type checker can see and what only
  runtime can.

Labels: **[Fact]**, **[Measured]**, **[Interpretation]**, **[Proposal]**, **[Decision]**,
as in the earlier entries.

---

## What landed

**[Fact]** An expression can declare **conditions** in two phases:
- `requires(...)`: what must hold before the path is used;
- `ensures(...)`: what must hold after it has been produced.

The conditions are:
- **existence:** `Exists` and `Absent`;
- **kind:** `File` and `Dir`;
- **capabilities:** `Readable`, `Writable`, `Creatable` and `Listable`;
- **containment:** `Under(base)`.

They live in `wend.conditions` and are re-exported from `wend`. The rules are in
[SEMANTICS.md §10](../SEMANTICS.md#10-conditions).

**[Fact]** Each property is enforced at a different point:

| what | enforced by |
|---|---|
| contradictory declarations (`Exists` with `Absent`, `File` with `Dir`, ...) | construction (`requires`/`ensures` raise) |
| nothing joined below a `File` | construction (`/`, `child`, `joinpath`, `under` raise) |
| `Under(base)`, lexically | every render: `render`, `resolve`, compiled renderers, `match`/`glob` verification, lenses, `resolve_frame` |
| `Under(base)` through symlinks, existence, kind, capabilities | `check` (preconditions), `confirm` (postconditions), `Step` |

**[Fact]** `Step(src=..., dst=...)` is the "one declaration" of a pipeline step.
- On entry, `with step(**bindings) as paths:` checks every precondition.
- On a clean exit, it checks every postcondition.
- `step.effects()` reports the declared effects as symbolic patterns, for example
  `<src: read {root}/raw/{name}.csv>` and `<dst: create {root}/out/{name}.parquet>`.

Errors are typed. Each also derives from the builtin that describes the same failure:

| error | also a |
|---|---|
| `MissingPathError` | `FileNotFoundError` |
| `PathExistsError` | `FileExistsError` |
| `CapabilityError` | `PermissionError` |
| `ContainmentError` | `InvalidBindingError`, so `glob` and `match` treat an escaping reading as a non-match |

## Decisions

**[Decision]** Conditions are metadata, outside equality and hashing, like the
derivations of §9.
- *Why:* a condition refines how a path may be *used*; it does not change which path
  is meant.
- *Consequence:* `e.requires(Exists) == e`, and dictionaries, lenses and `rebase`
  matching keep working unchanged.
- *Cost:* two equal expressions can render differently, because only one of them
  carries `Under`. §10 states this.

**[Decision]** Conditions belong to the expression they were declared on. Two
operations keep them:
- `bind`, which passes each `Under` base through the same bindings;
- `rebase`, which moves each `Under` base the same way the path moves.

Every other operation drops them, including one that returns an argument
unchanged; `_derived` makes a clean copy in that case. The alternative was to infer
conditions through operations: the parent of an existing file exists, and a
`with_suffix` of a readable file proves nothing. That would be a second semantics to
specify and test. Nothing in the essays asks for it.

**[Decision]** Lexical containment is conservative. A path is under its base when it
has the same anchor, the base's components come first, and no `..` follows them.
`/srv/a/../b` is refused even though it normalises inside `/srv`. Normalising `..`
lexically is wrong whenever `a` is a symlink, so the rule never relies on it. `check`
then compares `realpath`s.

**[Decision]** `Absent` uses `lstat`, so a broken symlink at the name counts as
present. An output declared absent must not be written through a dangling link.
`Exists` follows links, as `os.path.exists` does.

**[Decision]** `File` and `Dir` constrain only a path that exists. Add `Exists` to
require existence: `requires(File, Exists)` is pydantic's `FilePath`. A missing path
passes, so outputs can declare their kind before they exist
(`requires(Absent, File).ensures(Exists)`).

**[Decision]** Checks raise the first failure. Containment comes first, so no other
check looks at a path outside its base. A step stops at its first failing path.
Collecting every failure, for example as an `ExceptionGroup`, can be added later
without changing the declarations.

**[Decision]** `resolve_frame` checks containment row by row in Python, reusing the
same `contained`. A vectorised version would duplicate the rule in Polars string
operations. That is worth doing only if a workload needs it.

## Measurements

**[Measured]** Render cost on the shard expression `{root}/data/{split}/part-{idx:05d}.parquet`.
Minimum of 7×20,000 calls, interleaved with master:

| | master | this branch |
|---|---:|---:|
| `render`, no conditions | 6.2 µs | 6.2 µs |
| compiled, no conditions | 1.3 µs | 1.3 µs |
| `render` with `Under(root)` | — | 9.3 µs |
| compiled with `Under(root)` | — | 2.5 µs |

Expressions without conditions pay one attribute check.

Comparing `PurePosixPath` parts made the first version cost 15.4/8.3 µs. Rendered
strings are canonical, so `contained` now works on the strings. Its rule is checked
two ways:
- against the parts-based rule on all 3.09M pairs of canonical strings, built from
  every string up to 7 characters over `/.a` and up to 5 over `/.ab`, with no
  mismatch;
- a smaller exhaustive version is in the suite.

**[Measured]** Soundness and completeness of render's containment check were tested
on the contract's random terms. Bases were drawn from each term's derivation, plus
`.` and `/`. The check covers both the interpreter and the compiled renderer. The
property passed at 20,000 examples; the suite runs 500.

## Design note: static versus runtime

The issue asked what a type checker (pyright, ty) can check and what only runtime can.

| property | statically | at construction | at render (pure) | at check (point in time) |
|---|---|---|---|---|
| a `Segment`/`SubPath` binding cannot traverse | no: kinds are values | position rule (§2) | value rules (§3) | — |
| nothing is joined below a file | possible with a phantom parameter (below); not done | **yes** | — | — |
| contradictory declarations | no | **yes** | — | — |
| containment, lexically | no: needs dependent types | — | **yes** | yes |
| containment through symlinks | no | — | — | **yes** |
| existence, kind on disk | no | — | — | **yes** |
| capabilities | no | — | — | **yes** (`os.access`, real uid) |
| the effects a step may have | — | **from declarations alone**, without touching the filesystem | — | — |

**[Interpretation]** Part 2 is right that Python lacks the dependent types that
`Path[Under[root]]` needs. The base is a runtime value, and two paths under different
roots would need different types. A nominal brand per base (a `NewType`) can be
written, but nothing ties the brand to the base it names. Existence and capabilities
are facts about a filesystem *at a moment*. A type can at most witness that a check
happened once, and that witness goes stale (TOCTOU). `Annotated[Path, File, Exists]`
is transparent to type checkers by design. It is useful only as runtime metadata:
the conditions are plain objects, so `P(p).requires(*metadata).check()` validates an
annotated argument.

**[Proposal]** The one static property within reach is "nothing below a file",
using a phantom parameter. Under PEP 696, `PathExpr` would take a defaulted type
parameter, `class PathExpr[K = Unknown]`. `requires(File, ...)` would return
`PathExpr[IsFile]`, through an overload on a distinct singleton type for `File`.
`__truediv__` would be declared only for `self: PathExpr[Unknown | IsDir]`, so pyright
reports `config_file / "x"` as an error. The costs:
- every public operation's signature needs the parameter;
- results of `T()`, `bind` and `rebase` are `Unknown`;
- runtime already catches the mistake at construction, usually at import time.

I'd try it only after 0.2.0, as an experiment behind the existing runtime check.

**[Interpretation]** The issue asked whether the effects report needs the native IR.
It does not: the Python normal form plus declared conditions answers "what could this
step do, to which family of paths". Two harder questions are open:
- Do two steps' effects overlap (one writes what another reads)? That is the edge
  of Part 5's lazy-execution DAG.
- A precise answer needs an intersection test on two patterns, which wend lacks. Its
  matcher tests a concrete path against a pattern, not a pattern against a pattern.
  The test belongs with #29 (alternation and queries), which needs the same
  machinery for unions.

**[Proposal]** The race that matters most in practice is an output declared `Absent`
that appears between `check` and `open`. An atomic realisation closes it:
- `Step` could create outputs with `O_CREAT | O_EXCL`, so creation fails when
  `Absent` no longer holds;
- `O_NOFOLLOW` covers the final component of an `Under` path.

That is a small, opt-in effectful API (`step.open(name, mode)`). It would turn two of
the point-in-time checks into guarantees.

**[Proposal]** `glob` could take its default `kind` from a declared `File`/`Dir`.
That is cheap. I left it out to keep discovery independent of conditions until
someone needs it.

## Answers to the issue's open questions

- **Runtime-only, or also static?** Runtime, with construction-time checks where the
  facts are structural. One static experiment is proposed above.
- **`Annotated` or generics?** Neither is needed for the runtime design. The
  condition objects work as `Annotated` metadata. Generics are the route for the one
  static property.
- **How do capabilities compose through `parent`, `with_suffix` and joins?** They
  don't: conditions stay on the expression that declares them, and `bind`/`rebase`
  carry them.
- **Does the effects report need the native IR?** No; see above.
