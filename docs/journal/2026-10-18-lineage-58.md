# 2026-10-18: Lineage, before and after a path exists

This entry covers issue #28. Part 1 frames a path's future (intent, which
conditions and schemas now carry) and its past (lineage). The rules are in
[SEMANTICS.md §13](../SEMANTICS.md#13-lineage).

Labels: **[Fact]**, **[Interpretation]**, **[Decision]**.

---

## What landed

**[Fact]** The work has four parts:
- `PathExpr.tag(**kw)` adds tags as metadata.
- `wend.lineage` has three functions on expressions: `upstream`, `explain` and
  `tags`.
- A `Ledger` records artefacts in an append-only JSON-lines file. It answers
  `provenance`, `upstream`, `downstream` and `stale`, and `run(step, ...)`
  records a `Step`.
- Content keys: `content_key(*paths)` is an effect, and `values_key(**values)`
  is pure.

## Decisions

**[Decision]** Lineage lives on both sides, as the issue's first open question
anticipated:
- **Static lineage is the derivation.** #26 already records how each
  expression was built, so `upstream` and `explain` walk it. Part 2's complaint
  that ".parent lops off the structure" no longer holds: a parent keeps a
  record of what it is the parent of.
- **Dynamic lineage is a ledger.** A file's past is a fact about the world,
  so it is recorded as data, with content digests, not inferred.

**[Decision]** Tags are metadata like conditions, and they don't propagate by
copying.
- `bind` and `rebase` keep them.
- Every other result starts clean.
- `lineage.tags(e)` collects the tags of everything `e` was derived from, so a
  report built from a tagged upload is found to come from an upload. That is
  by derivation, without every operation copying dictionaries.
- `_derived` and the conditions' `attach` now carry or drop tags by the same
  rule as conditions.

**[Decision]** The ledger records relations; it does not schedule.
- `downstream(changed)` lists what to rebuild, and `stale(path)` says whether
  an output is out of date.
- Deciding the order, running the steps and caching results belongs to the
  caller or to a workflow tool such as Snakemake, DVC or Nix.

That answers the issue's second open question, where to draw the boundary:
wend provides the relations, the recorder and the checks.

**[Decision]** A content key is a plain value, not a parameter type. The third
open question offered a parameter type, a `Lens`, or a separate construct.
- A key computed inside `render` would make rendering read files.
- So the key is computed by a helper and bound like any value. `render` stays
  pure, and `match` reads the key back.
- Whether the key still names its inputs is a check done now: recompute it and
  compare.

`values_key` covers Nix's other half: a path named after its build
instructions.

**[Decision]** `Ledger.run` derives what to record from the step's declared
effects (#27):
- outputs are the paths a step creates, writes or deletes;
- inputs are the paths it reads;
- the bindings recorded for an output are those its expression uses;
- the tags are the output's lineage tags.

A body that raises records nothing, because the postconditions never ran.

**[Decision]** Each record stores paths absolute and normalised, and the
latest record for a path is its provenance. Re-running a step appends rather
than rewrites, so the history stays available in `records()`.

## Limits

**[Interpretation]**
- `stale` checks one level. Transitive staleness is `stale` combined with
  `downstream`, which the example shows. A recursive `outdated(path)` is easy
  to add once a use asks for it.
- The ledger is a local file, with no locking for concurrent writers. Appending
  whole lines is atomic for small records on POSIX filesystems, but concurrent
  pipelines need a lock or a database.
- Digests read whole files. `Ledger(digests=False)` records relations only, for
  large artefacts where only the graph is needed.
