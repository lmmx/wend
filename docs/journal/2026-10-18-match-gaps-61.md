# 2026-10-18: The last format-spec gaps between render and match

This entry covers issue #55: the cases where `render` raised the wrong error,
or `match` raised or missed a reading, because of a format spec. The rules
are in [SEMANTICS.md §4 and §7](../SEMANTICS.md#7-matching).

Labels: **[Fact]**, **[Measured]**, **[Decision]**.

---

## Rendering

**[Decision]** Every value that `format` rejects is an invalid binding. That
covers `TypeError`, `ValueError` and `ArithmeticError` (the base of
`OverflowError`), on every route: segment values, fields, nested spec values
(`{x:{w}}`), `bind` and the compiled renderer.

Before this change, `{n:c}` bound to -1 and `{n:f}` bound to 10**400 raised a
raw `OverflowError`. Any other exception still propagates, since it is a bug
in a value's own `__format__`.

**[Fact]** Error messages used `repr`, and `repr` itself raises `ValueError`
for an int over 4300 digits. So the message replaced the error it was
describing. Messages now go through `errors.show`, which never raises.

## Matching untrusted text

**[Decision]** Reading text never raises. Text that a parser rejects gives
no candidate, whatever the parser raises:
- `literal_eval` under `!r`/`!a`;
- a declared type's constructor, such as `Decimal("abc")`.

Formatting a candidate during verification catches everything for the same
reason.

**[Decision]** Text shorter than its spec's width, or than its precision
under `fFeE%` or a float's alternate `g`, has no reading. `inf` and `nan`
are the exception, since they ignore precision.

**[Measured]** A width can be read from the path itself
(`{w:d}_{u:{w}}`). Before, matching `99999999_x` took 79 ms and peaked at
100 MB, and each further digit multiplies that by ten. It now takes 2 ms and
0.2 MB.

**[Fact]** The bound holds for the standard mini-language:
- a brute-force check found no case where text `format` actually produced
  was judged too short;
- it covered 432,200 combinations of value (str, int, bool, float and
  Decimal, including inf, nan and sNaN), spec and conversion.

The check found that Decimal's alternate `g` drops trailing zeros, so that
clause applies to floats only. Types with their own `__format__` are not
pruned.

## Readings

**[Decision]** A bool formats as `True`/`False` only under the empty spec,
and as the int 1 or 0 under any other. A bool field reads exactly those
texts.

The same cause had two neighbouring gaps:
- an int field under a float type reads `5.000000` as 5;
- a typed field under `!s` reads `T(text)`.

**[Decision]** An untyped field without a presentation type reads the first
of `str`, `int`, `float` that formats under its spec:
- a str refuses a sign, `z`, `#`, grouping and `=`;
- an int refuses `z` and a precision.

So `{u:+5}` reads an int and `{u:z}` reads a float. #45's zero-padding rule
(`{u:05}` reads str and int) stays, except under a precision.

The rule adds no ambiguity. Where it chooses int, no str formats under the
spec, so the field reads exactly what a `type=int` field reads.

**[Decision]** Where completeness cannot hold, §7 says so:
- a str precision truncates;
- float types round;
- an untyped spec does not read floats where it reads str or int;
- `n` assumes the C locale;
- `!r` cannot read `inf`/`nan`.

Soundness still holds in each case: every returned binding renders the path.

## Left open

- A Decimal field reading `sNaN` raises `InvalidOperation`, because two equal
  sNaN candidates are compared with `==`.
- `literal_eval` prints a `SyntaxWarning` for texts with invalid escapes.
  Suppressing it needs `warnings.catch_warnings`, which is not thread-safe on
  default builds.
- A field declared with a tuple of types (`type=(int, str)`) reads nothing.
- `T(t"{-1:c}")` raises `OverflowError` when it is built, as the f-string
  would.
