# 2026-10-22: When two strings name one file (research)

[The knowledge model](2026-10-22-knowledge-states.md) and
[the analysis of path families](2026-10-22-symbolic-families.md) rest on two
assumptions: a closed world, and *lexical identity*, under which different rendered
strings name different files. This entry breaks the second on disk, builds a model
that does not need it, and finds three counterexamples to that model. It also finds a
defect in a core check, and shows how the kernel can enforce lexical identity at the
moment a path is used.

The prototype is `wend._experimental.identity`, with tests in
`tests/aliasing_test.py`.

Labels: **[Fact]**, **[Measured]**, **[Proven]**, **[Interpretation]**,
**[Conjecture]**, **[Proposal]**.

## 1. The string-keyed tracker, broken on disk

**[Measured]** Each case below is a test that runs `knowledge.Tracker` on a real
directory and finds a known fact that is false:

| alias | the pipeline | known, and false |
|---|---|---|
| symlinked directory | read `link/x`; delete `d/x` | `exists(link/x)` |
| `..` spelling | read `d/../a`; delete `a` | `exists(d/../a)` |
| bind mount of `d` at `m` | read `m/x`; delete `d/x` | `exists(m/x)` |
| output made as a symlink | create `o` as a link to `t`; delete `t` | `exists(o)` |

**[Fact]** Lexical normalisation does not repair this. If `d` is a symlink to
`far/deep`, then `d/../a` is `far/a`, while `os.path.normpath` says `a`. The kernel
resolves `..` physically.

**[Fact]** Two cases break atoms in neither tracker:
- **Hard links.** Two entries name one file. Deleting one entry leaves the other, so
  no atom goes stale. Writing through one changes what the other holds, which matters
  to content and lineage, not to atoms.
- **A writer outside the program.** This breaks both trackers, as the closed world
  says it must. An open file survives it (§6).

## 2. Keying a fact by what its check reads

**[Fact]** `resolve(path)` walks the path component by component, as the kernel does:
`..` goes to the physical parent, symlinks are followed (a final one too), and the
walk ends at the first missing entry. It records a *trace*:
- every directory entry looked up, as (device and inode of its directory, name);
- every directory passed through;
- the entry where the walk ended, followed (`final`) and not followed (`lfinal`);
- the object it reached, if any;
- for a missing path, the nearest existing ancestor as `wend.conditions` finds it.

**[Fact]** A fact is keyed by what its atom's check reads (`_key`):

| atom | the check (§10) | key |
|---|---|---|
| `absent` | `lstat` fails: a final symlink is itself an entry | the entry, not followed |
| `create`, `write` of a missing path | the nearest existing ancestor is a writable, searchable directory | that ancestor |
| every other atom | `stat` and `access` of the object reached | the final entry, followed |

For a missing path, the final entry is the first missing one, and the components past
it are never read.

**[Fact]** A mutation of `m` forgets a fact when one of three things holds:
- the fact's trace looked up `m`'s final entry, which covers `m`, every path through
  `m`, and the parents that making `m` may make;
- the trace passed through `m`'s directory, however that directory was reached (a
  bind mount reaches it through another entry);
- the trace reached `m`'s object (another name of it).

**[Proven]** *Soundness, under the assumptions below: at every step's entry, every
atom the identity tracker reports known holds of the path being checked.* This holds
for any spelling of the path, not only for the facts as stored. It follows from two
lemmas, by the same induction as the knowledge model's §3.

- **Key lemma.** Let two traces of an atom have one key, and let nothing in the first
  trace's entries, directories or object have changed between them. Then the checks
  give one outcome. Take the table's rows:
  - `stat`, `access`: the final entry is unchanged, so it is missing for both, or names
    one object, whose kind and permission bits are unchanged.
  - `lstat`: the same argument for the unfollowed entry.
  - Creation: the ancestor is one directory, its own entry is in the trace, and its
    permission bits are unchanged.
- **Forget lemma.** A mutation of `m` changes three things at most: the entry at `m`'s
  final position (made, removed or replaced, together with the missing parents
  `mkdir -p` makes below the first missing entry), `m`'s object, and what lies below
  `m`'s directory. Each is a clause of the forget rule.

**[Fact] Assumptions:**
1. **The closed world.** The namespace changes only through the declared mutations of
   steps, and no permission bits change.
2. **Mounts stay put** during a run.
3. **Exact names.** Two different names in one directory are two different entries.
   Case-insensitive and normalising filesystems break this (§7).

**[Fact]** Reusing an inode number cannot make a fact wrong under assumption 1.
Deleting the old object's entry already forgot every fact that reached it.

**[Interpretation]** Resolving a trace makes the lookups a check makes. So the identity
model is not a way to skip checks: it costs what it would save. It is a *reference
semantics*: the knowledge a string-keyed model should approximate, and the oracle to
test one against. §5 and §6 are the cheap routes.

## 3. Counterexamples to the identity model

**[Measured]** The first version keyed every atom by the followed final entry. Its
tests checked each stored fact against the path it was stored for, and passed 400
examples. A stronger oracle checks every atom reported known at a step's entry against
the path being checked, with elision on so the step runs. It failed at once, three
ways:

| defect | counterexample | on disk |
|---|---|---|
| `absent` followed a final symlink | delete `d/x`, then create `lx`, a link to `d/x` | `lx` is not absent (`lstat` sees the dangling link), but `absent(d/x)` answered for it. With elision, the create ran and wrote `d/x` *through* the link; the check that would have refused it was skipped. |
| a path below a file shared the file's key | read file `f`, then require `exists(f/x)` | `exists(f/x)` known; `f/x` cannot exist |
| creation was keyed by the first missing entry | `lnk/x` with `lnk` a dangling link to `far/missing`, and `far/missing/y` | one first missing entry, but `Creatable` consults `r` for the first and `far` for the second. With `far` read-only, one passes and one fails. |

**[Interpretation]** "Do these two strings name one file?" is the wrong question. Two
paths share a fact when their *checks read the same state*, and that differs by atom:
`stat` and `lstat` read different entries of one spelling, and a creation check reads
an ancestor chosen from the spelling. A fact's identity is the read set of its check.

**[Fact]** The read-only case needs a read-only bind mount. Root ignores permission
bits, but not `EROFS`. It is the first way found in this container to make `access()`
refuse; until now no test could exercise a refused permission on disk.

## 4. A defect in `Creatable`

**[Measured]** `Creatable` passes for a path whose resolution crosses a dangling
symlink, and then no way of creating the path works:
- **Link in the middle.** For `lnk/x`, with `lnk` dangling, `mkdir -p` fails with
  `EEXIST`, because `lnk` occupies the name.
- **Link at the end.** For `o`, with `o` linking to a missing `far2/t`:
  - `open(o, "x")` fails with `EEXIST`;
  - `open(o, "w")` follows the link, and here fails with `ENOENT`. Where the link's
    directory exists, it creates the file *wherever the link points*.

**[Fact]** The cause is `_ancestor`. It walks up the spelling with `os.path.exists`, so
it steps over a component that exists as a dangling link. It then reports that the
link's parent is writable, which is not where creation would happen. With the link
target's directory read-only, `Creatable(lnk/x)` still passes (§3).

**[Proposal]** A component that `lstat` finds but `stat` does not (a dangling link or a
loop) should make `Creatable` and `Writable` fail, with "is a broken symlink".

**[Conjecture]** With that change, the nearest existing ancestor is the directory of
the first missing entry, for every path, and the creation row of §2 needs no key of
its own. The argument:
- existence is monotone along prefixes, since resolving a longer prefix resolves each
  shorter one;
- without dangling links, the longest existing prefix resolves to the directory where
  the walk failed.

This is a core change, so it is proposed here and not made.

## 5. The bridge: alias-free runs

**[Fact]** `Trace.alias_free(root)` holds when, strictly below the root's physical
path, the walk followed no symlink, took no `..`, and entered no mount point (read
from `/proc/self/mountinfo`). Above the root, resolution is shared by every path below
it. `IdentityTracker.alias_free(root)` says this of every path a run resolved.

**[Proven] Uniqueness lemma.** Take two canonical strings below one root, without `..`,
whose walks are alias-free below it. Then:
- they name one entry exactly when they are equal;
- one lies below the other exactly when it is a string prefix of the other.

The argument, by induction on the components below the root:
- each lookup is the name looked up in the directory the string's prefix reached;
- equal prefixes reach one directory;
- different names in one directory are different entries (assumption 3), and the
  subtrees below them are disjoint. No hard links to directories exist, and no mount
  is crossed.

**[Proven] Corollary.** On an alias-free run, the knowledge model's lexical identity
holds for every path the run resolved. By the lemma, equality and prefix order of the
strings are identity and nesting of the entries. The knowledge model's proof (§3
there) then applies unchanged. Hard links remain, and the proof does not need them
excluded: a mutation through one name changes no atom of another (§1). So
string-keyed knowledge of atoms is sound on every alias-free run. The analysis of
families keys facts by strings, so this is also the condition under which its lexical
identity holds.

**[Measured]** 2,000 pipelines over random trees with aliases, half of whose
spellings are drawn from the alias class of an earlier step's:

| measure | string-keyed | identity-keyed |
|---|---|---|
| pipelines with a known fact that is false | 189 | 0 |
| entries with such a fact | 539 | 0 |
| atoms reported known, false of the path checked | 22 | 0 |
| pipelines where elision changed an outcome or the final tree | 2 | 0 |
| atoms known at entry, of 8,399 required | 782 (9%) | 1,429 (17%) |

| runs | count | string-keyed knowledge wrong |
|---|---|---|
| alias-free | 337 | 0 |
| with an alias | 1,663 | 189 |

**[Interpretation]** The identity model knows more as well as knowing correctly. It
shares facts between spellings. It also keeps creation facts that the string model
must forget when a parent is not known to exist: here, a creation fact depends only on
its ancestor.

## 6. Enforcing it at the moment of use

**[Fact]** Checking alias-freedom costs a walk, and holds only when it was checked.
`openat2(2)` (Linux 5.6) can instead make the kernel refuse every other reading, at
the moment of use. `Beneath(root)` opens paths relative to a descriptor for the root
with three flags:
- `RESOLVE_BENEATH`: never above the root;
- `RESOLVE_NO_SYMLINKS`: no symlink, at any component (`ELOOP`);
- `RESOLVE_NO_XDEV`: no mount crossed, bind mounts included (`EXDEV`).

It also refuses `..` components and absolute paths itself. Every resolution that
succeeds is then alias-free in §5's sense.

**[Measured]** Agreement with the model: over 400 random alias trees and spellings,
`Beneath.stat` succeeded exactly where the trace said the path exists and
`alias_free` holds. A bind-mount test covers mounts. The kernel is the oracle here for
the model's `alias_free`, and it agreed every time.

**[Measured]** Time of check against time of use:
- **A swap after the check.** A file is checked `File`, `Exists` and `Readable`, then
  swapped for a symlink to a file outside the root. A plain open reads the outside
  file. `Beneath.open` fails with `ELOOP`.
- **Writing through a dangling link.** A plain `open(p, "w")` on a link to `../pwned`
  creates `pwned` outside the root. `Beneath.create` (`O_CREAT | O_EXCL`) refuses, and
  makes `Absent` and creation a single system call.
- **An open file.** `Held` (or `Beneath.hold`) keeps a file open. Its kind, the access
  it was opened with, and what it reads all survive unlinking, renaming or swapping
  its name.

**[Interpretation]** Here is the architecture this suggests:
- `Under(root)` declarations make every rendered path canonical and below the root,
  without `..` (`contained`, §10);
- executing the pipeline's opens through `Beneath(root)` makes every resolution
  alias-free, as the kernel guarantees;
- the analysis of families keys facts by strings, and needs lexical identity. With
  both of the above, that assumption is *discharged by construction* rather than
  assumed;
- what remains is the closed world against other writers, and case folding. Even
  there the failure is closed: a known fact that an outside change has made wrong
  ends in `ELOOP`, `EXDEV` or `ENOENT` at the open, not in a read of another file.

**[Fact]** This is the discipline of capability-based filesystem APIs. The
[cap-std](https://github.com/bytecodealliance/cap-std) README describes opening
beneath a directory with `openat2` on Linux 5.6+, and with `O_RESOLVE_BENEATH` on
FreeBSD 13+. The [man page](https://man7.org/linux/man-pages/man2/openat2.2.html)
notes that `RESOLVE_BENEATH` was modelled on FreeBSD's `O_BENEATH`. What wend adds is
the static side: an analysis, before any binding, of which facts survive which steps.

## 7. What this means for check events and capabilities

**[Interpretation]** The owner asked for postconditions as check events with explicit
temporal scope (decision 2). Three kinds of certification now have different
lifetimes:

| | what it certifies | how long |
|---|---|---|
| a check of a name (`Checked`, a future `Confirmed`) | atoms held of a path when checked | that moment |
| knowledge of a name | the check, and no mutation since that reads its key | until a mutation that `affects` it, under the closed world |
| a held object (`Held`) | kind and access of an open file description | while it is open, whatever happens to names |

**[Proposal]** For a typed step API:
- inputs are opened beneath the root and *held*, so the checks are made on the
  descriptor the body reads, and their facts persist;
- outputs are made with `Beneath.create`;
- a name's facts stay check events, with knowledge as the dataflow over them.

This separates what types can certify durably (facts of held objects) from what only
an analysis can (facts of names over time).

## 8. Mutants

**[Measured]** Each rule was mutated, and every mutant is rejected:

| mutant | rejected by |
|---|---|
| `absent` follows a final symlink | the targeted test (the elision property, under some seeds) |
| a path below a file is the file | the generated known-atoms property, and a targeted test |
| creation keyed by the first missing entry | the read-only bind-mount test only |
| final symlink not followed | the generated known-atoms property |
| no entry clause | two generated properties, and a targeted test |
| no directory clause | the bind-mount deletion test |
| no object clause | the hard-link test |
| `alias_free` ignores symlinks, or `..` | the kernel-agreement property, and the bridge property |
| `alias_free` ignores mounts | the bind-mount `Beneath` test |
| `alias_free` takes the root as spelled | a targeted test, with the root reached through a symlink |

**[Fact]** Two candidate mutants were equivalent, and the code took the simpler form:
- forgetting by the unfollowed entry as well: every trace that looked a link up
  followed it to the same final entry;
- comparing the components past the first missing entry.

**[Fact]** The creation mutant survives every generated test, because as root no
directory here refuses writes without a read-only mount.

## 9. Limits

- **[Fact] Case folding is untested.** This kernel was built without
  `CONFIG_UNICODE`, so a case-folding ext4 cannot be mounted here.
  - For existing entries, the object clause forgets two spellings together.
  - For missing ones, `absent(Data)` survives the creation of `data`. That is
    unsound, and the model says so (assumption 3).
- **[Fact]** Changes of permission bits, mounts, renames, and fsspec stores are not
  modelled.
- **[Fact]** `Beneath` is Linux only, and `RESOLVE_NO_SYMLINKS` refuses symlinks that
  users may rely on. The man page advises making it configurable unless it has a
  security purpose.
- **[Fact]** The proofs above are arguments written out, not checked by a machine. The
  tests check their conclusions on disk.

## Addendum: audit (2026-10-22)

The journals of the research stack were audited against the commits, the tests and the
session record. This entry was thorough on its results. What follows corrects one claim,
records what happened to §4's proposal, and keeps the development of §8, which the table
there flattens.

### A.1 Withdrawn: "the failure is closed" (§6)

**[Refuted]** §6 said that under confinement, "a known fact that an outside change has
made wrong ends in `ELOOP`, `EXDEV` or `ENOENT` at the open, not in a read of another
file". #112 found two counterexamples. Both resolve beneath the root and pass every
path check:
- **a hard link to a file outside the root**: it is read, and overwritten through, with
  no error (`2026-10-22-confined-runs.md` §2 and §4);
- **a FIFO in place of an input**: the open blocks for ever.

Confinement of *resolution*, which `openat2` gives, is not confinement of the *object*
reached. #112 added judgement on the descriptor: a regular file or directory, one name
(`nlink == 1`), opened non-blocking, truncated only after the judgement.

`identity.Beneath.hold`, which §6 and §7 propose for inputs, still opens without that
judgement. Only `confined.Confined._open` and `events.Run` judge objects.

**[Interpretation]** §1's conclusion still stands: hard links are harmless to *atoms*,
because an atom is a property of a name and of the object it reaches. For confinement
they are an escape. The two entries answer different questions, and neither says so.

### A.2 What became of §4's proposal: #111

**[Fact]** The fix proposed in §4 was made in #111 (355ea00), which is unmerged:
`Creatable` and `Writable` fail for a path whose resolution crosses a dangling link, or
a loop, with "is a broken symlink". Its record:
- **The choice put to the owner.** Refuse at the dangling name. The alternative was to
  judge the directory the link points into.
- **The contract property.** For a missing path, `Creatable` holds exactly when making
  the parents and then the path, exclusively, succeeds. On master it fails with
  `(['broken'], True, False)`.
- **Loops.** A symlink loop stays indeterminate.

**[Fact] Its interaction with this entry.**
`test_a_missing_paths_creation_is_judged_where_the_check_looks` relies on
`Creatable(lnk/x)` *passing* across a dangling `lnk`, which #111 makes fail. That test is
also the only one that rejects the "creation keyed by the first missing entry" mutant
(§8). Merging #111 therefore needs the test rebuilt. That also makes §4's conjecture
testable: with #111, creation needs no key of its own.

### A.3 How the mutation suite acquired its teeth (§8)

**[Measured]** §8 gives the final state, where every mutant is rejected. The first round
was different:
- **1 of 5 mutants detected at first.** The rest were reported "NOT DETECTED".
- **The `..` mutant was ill-formed.** `if c == ".." and False` still resolves `..`
  physically, through the directory entry. It was replaced by a mutant that normalises
  the path first. The table above lists the replacement only.
- **"Final symlink not followed"** survived generators that drew spellings uniformly. It
  died once half of each pipeline's spellings were drawn from the alias class of an
  earlier step's.
- **"Creation keyed by the first missing entry"** survived until its test spanned two
  steps. The reason is a property of #108's model:
  - a port that requires `Creatable` declares `create`, a mutating verb;
  - so its own creation fact is forgotten at exit;
  - creation knowledge outlives a step only as a postcondition.

  `2026-10-22-knowledge-states.md`'s addendum records it there.
- **"`alias_free` takes the root as spelled"** survived until a targeted test reached the
  root through a symlink.
- **A harness defect, checked here.** In #114's harness a mutant that does not compile
  read as a survivor. The same flaw existed in this entry's mutant harness and #112's.
  The audit compiled every mutant of both against the current sources: all compile, so
  no result here was affected.

**[Fact] A test that kills a mutant for the wrong reason.** "No object clause" is
rejected by `test_two_names_of_one_object_are_forgotten_together`. That test asserts a
*design choice*: two names of one object are forgotten together, which is conservative.
It does not catch a false known fact. §1 shows hard links break no atom. The clause's
real purpose is case folding (§9), which this kernel cannot test.

### A.4 Missing from the text

- **[Measured] How bind mounts were found.** For a bind mount within one filesystem,
  `os.path.ismount` is false and `st_dev` is unchanged. Only `/proc/self/mountinfo`
  shows it. That is why `alias_free` reads mountinfo, and why it returns false when
  mountinfo cannot be read.
- **[Fact] The repair of the "below a file" defect (§3).** A path below a file is keyed
  by a pseudo-entry: the file's identity paired with the next name. That entry is both
  an entry and missing (`identity.resolve`).
- **[Fact] Privileged tests skip silently.** The mount tests call
  `pytest.skip("cannot bind-mount here")`, and a writer's `mount` move does nothing when
  `mount` fails. Four mutant kills come only from such tests:
  - no directory clause;
  - creation keyed by the first missing entry;
  - `alias_free` ignores mounts;
  - deletion entering mounts.

  Unprivileged CI would run none of them. There is no Linux skip marker either: on
  another system these tests would error (`O_PATH`, `/proc/self/mountinfo`) rather than
  skip.
