# 2026-10-25: Depths through shared SubPaths and changed names (#129)

`relate` has long decided by depth where two remainders hold segments alone
(`docs/SEMANTICS.md` §15.3, 5): each renders a fixed count of segments. Among the
`"unknown"` answers the overlap analysis confirmed as YES but no search could witness,
some are plain depth arguments that pass through a `SubPath` or a changed name.
`({root}/{n:d}.{p}/{s...}).with_suffix("")` renders `2 + |s|` segments below `{root}`,
and `{root}/{n:d}.{p}/{n:d}.{p}/{s...}` renders `3 + |s|`: never one path. This entry
extends the depth rule to whole expressions.

## 1. The rule, and why it is sound

**[Proven]** Write the depth of a rendered path as the number of its segments after the
anchor, as `lexically` counts them. For an expression `e`, `_depth` gives a count `n` of
segments and a list of *parts of varying count*:
- a literal head contributes none, and any other head (a head parameter, a deferred
  operation other than those below) is itself a part of varying count;
- a segment contributes one segment (§3: never `""`, `.` or a separator), and a
  `SubPath` is a part of varying count;
- `with_name`, `with_suffix` and `with_stem` keep their base's count: pathlib replaces
  the last segment, and refuses where there is none, so wherever the change renders,
  its depth is its base's;
- a parent has one fewer, where its base has a segment of its own (`n ≥ 1`): pathlib's
  parent drops the last segment, `..` included, wherever there is one.

Rendering joins these pieces, and joining relative pieces adds their segments, so on
every binding `e` renders `n` segments plus those each part of varying count renders on
its own.

Under shared bindings a part alike on both sides by (1) renders one text on both, and
so one count of segments. Its key is equal, and no name in it has a different default
on each side. So where the parts of varying count on one side are, counted with their
multiplicity, alike those on the other, the two depths differ by `n − k` on every
binding where both render:
- they are never the same unless `n = k`;
- `a` is never strictly inside `b` unless `n > k`;
- `a` never contains `b` unless `n < k`.

Under independent bindings only expressions with no part of varying count are decided.
That case is the one the existing rule already covers, extended through changed names
and parents.

**[Fact]** The rule asks nothing of how the paths align, so it decides pairs the
overlap analysis leaves at MAYBE or at an unconfirmed YES. On #119's samples, before
parents were counted:
- a rule on the remainders alone, after prefix cancellation, decides 33 answers;
- this rule decides 137;
- the two together decide 139.

The remainder rule was dropped, since its two extra answers do not pay for a second
rule. Counting parents brings this rule to 144.

## 2. Tests and measurements

**[Measured]** `test_a_depth_counts_the_segments_rendered` checks `_depth` itself
over 300 generated expressions. They are built from a base, perhaps ending in a
`SubPath`, under up to two deferred operations (parents, paths made relative, changed
names), with parts joined on. On every pooled binding, the rendered path has `n`
segments plus those each part of varying count renders alone. 296 of the 300 have a
known depth: 211 with parts of varying count, 113 with a deferred head among them, and
20 with a parent. There are 25,195 renderings.

**[Measured]** `test_depths_decide_with_shared_subpaths` holds the examples:
- the changed name above, which is decided only under shared bindings;
- a parent beside a changed name;
- `{s}/{s}` and `{s}/a`, which are one path where `s` is `a`, so multiplicity counts;
- a `SubPath` defaulted differently on each side, which decides nothing.
